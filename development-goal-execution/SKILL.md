# 开发目标执行

把一个开发目标拆成六道门来做：上下文恢复、第一性规划、第三方评审、规范化执行、全覆盖验收、对抗式审查。前面多花 token，是为了少返工。省 token 去跳门，这个技能就没用了。

这是流程，不绑某个智能体，也不绑某个审查工具。能读仓库、改文件、跑检查，就可以按这套做。

加载本技能，只说明适用这套流程。用户点名哪个阶段，就做到那个阶段停。没说执行，就不要改代码。

## 何时用

- 用户给的是开发目标，不是一次性小改
- 用户点名了下面某个阶段
- 用户宁可多走几步，也不要后来返工

## 何时不用

- 改错字、改注释、改一行配置，而且对不对一眼能看出来
- 单纯排障：先排障。修这个 bug 本身变成目标时，再回来
- 纯调研、只读提问，并且不是在做计划评审

用户已经有批准过的计划、只要执行：仍用本技能，从「执行计划」开始，不要重写方案。

## 为什么费 token

恢复上下文、按第一性原理写计划、审计划、验收、对抗式审查，都会费 token。费在这里，是为了在动手之前拆掉错误方案，在收工之前拆掉站不住的完成结论。

改动看起来小，或用户在等，都不能拿来当跳门的理由。

## 用户点名的阶段

下面这些是阶段叫法。点了其中一个，不表示要做完全程。

缺前面的步骤时，只补到被点名的阶段，然后停。没点名的后面阶段，不要接着做。

| 用户说的 | 对应门 | 做什么 | 停在 | 不要做 |
|---|---|---|---|---|
| 开发目标 / 三阶段 | 全部六门 | 完整流程 | 对抗式审查 PASS | — |
| 实施与验收计划 | 1 上下文恢复、2 第一性规划 | 先恢复上下文，再写出计划 | 计划本身 | 评审、执行、验收 |
| 计划评审 | 3 第三方评审 | 没有计划就先写计划，再评 | 评审结论 | PASS 之后动手 |
| 执行计划 / 评审通过后执行 | 4 规范化执行 | 只做已批准范围 | 实现完成、可以验收 | 重写方案、扩大范围 |
| 执行后验收 | 5 全覆盖验收 | 按已批准的项做验收 | 验收结果 | 顺手加功能 |
| 验收通过为止 | 5 全覆盖验收 | 验收；失败就修原因再验 | 验收 PASS，或真实阻塞 | 扩成新目标 |
| 对抗式审查 | 6 对抗式审查 | 证明完成结论不成立 | 审查结论 | 把审查当成没做完的活接着干 |

被点名的阶段缺前置时（没有可评的计划、没有已批准范围、没有可验的实现）：补上前置，做完被点名的阶段，然后停。

## 计划必须先被别人审

写计划的人不能自己批这个计划。审过之前，不要开始实现。

优先找独立、只读的审查方：另一个会话、另一个模型、另一个子代理，而且不是这份计划的作者。用户点了审查方，就用那个。叫什么名字，要求一样。

审查结论只认 `VERDICT: PASS` 或 `VERDICT: FAIL`。提问、部分同意、缺证据、「看起来可以」，都不算过。

没有独立审查方时，把计划交给用户，等明确批准。用户批准算过。自己评自己不算。

## 完整流程

只有用户要完整目标（`开发目标` / `三阶段`），或把剩下的阶段都点名了，才走完下面六步。

1. **上下文恢复**
   - 读和目标有关的仓库现状、已有文档、既有决定、测试，以及脏工作区边界。
   - 写明：读过什么、推断了什么、什么还没核实。
   - 已核实的约束，和沿用下来的假设，分开写。已有设计和用户原话，都不能证明某个方案必须存在，或一定正确。

2. **第一性规划**：按第一性原理写实施与验收计划
   - 先还原：真正的问题、必须达成的结果、不能破坏的条件、约束、怎样算失败。然后再选方案。
   - 每个部件都问一句：没有它行不行。在已核实的约束下，选最小的方案。
   - 计划要具体到可以直接执行，不能做到一半再发明步骤：
     - 目标、范围、明确不做的事
     - 涉及的文件、模块
     - 实施步骤
     - 验收项：命令和预期结果；需要的话再加上界面、手工、现场检查
     - 风险、回滚、兼容
     - 还没核实的事项
   - 不要换一套更空的话把目标再说一遍。目标没要求的架构、服务、文档、抽象，不要加。

3. **第三方评审**：先审计划，再写代码
   - 不要开始实现。
   - 优先交给独立、只读的审查方，只要 `VERDICT: PASS` 或 `VERDICT: FAIL`。
   - 没有独立审查方，就把计划交给用户，等明确批准。
   - `FAIL`、不是 PASS、或用户否决：改计划再送审，或报告阻塞。

4. **规范化执行**
   - 只做已批准范围。
   - 用户改过的文件，以及无关的脏文件，不要动。
   - 行为已经让旧注释、旧文档变错了，才改那些文字。
   - 批准范围里该用 TDD、排障、代码审查，就用。本技能管先做什么后做什么，不管那些具体技法。

5. **全覆盖验收**
   - 已批准计划里的验收项，全部跑完。
   - 失败就修原因，再跑失败项和受影响的项。
   - 验到 `PASS`，或留下真实的外部阻塞。

6. **对抗式审查**
   - 验收通过后，先当完成结论是错的，再去查。
   - 查：站不住的假设、没走的路径、边界、回归、范围是不是漂了、现有证据能不能撑住这个目标。
   - 优先用独立、只读审查方，要求和审计划相同。没有独立审查方，就把完成结论和证据交给用户，等明确批准。
   - `FAIL`、用户否决、或任何不是 PASS 的结果：修原因，重跑受影响的验收，再审。
   - 审查或用户批准通过之前，不能说做完了。

## 何时停

这些情况直接报告阻塞，不要空转：

- 缺依赖，或环境连不上
- 产品选择要用户拍板
- 计划或完成结论正在等用户批准
- 某项验收跑不了
- 用户自己的脏文件和已批准范围打架
- 被点名的阶段已经做完

## 这些情况说明做错了

- 用户只让评审，却开始写代码
- 用户要完整目标，计划还没被别人审过，就开始写代码
- 自己评自己，还把它当成已经审过
- 觉得「脑子里已经验过」，就跳过验收
- 没做对抗式审查，也没得到用户批准，就说做完了
- 既然已经在改，就顺手加架构
- 评审 `PASS` 之后，接着做用户没点名的下一阶段

| 常见借口 | 实际情况 |
|---|---|
| 他说了计划评审，PASS 之后就该实现 | 评审做到结论就停。等他说执行。 |
| 太小，不必过门 | 小改动也会回退。过门比返工便宜。 |
| 自己审一下，省 token | 自己审不算。找审查方，或问用户。 |
| 没有现成审查方，这门跳过 | 这门是「计划要被别人审」，不是某个工具名。问用户。 |
| 用户在等 | 跳门之后的返工，才是这个技能要挡住的。 |
| 审查方在提问，差不多就算过 | 提问不是 `PASS`。 |
| 我已经知道设计是对的 | 这是假设。送审就是来查这个的。 |

## 计划评审提示

```text
只读计划评审。不要改文件。你不是这份计划的作者。

目标：<开发目标>
计划：<实施与验收计划>
已读证据：<看过的文件、文档、测试、日志>
风险点：<已知风险>

返回：
- VERDICT: PASS 或 FAIL
- 只写阻塞问题
- 缺验收证据的，写明缺什么
```

## 对抗式审查提示

```text
只读对抗式审查。不要改文件。先当工作没做完，试着证明完成结论不成立。

目标：<开发目标>
已批准范围：<已批准的实施计划>
变更：<改了哪些文件和行为>
验收证据：<命令、测试、日志或检查，以及结果>
已知限制：<还没核实，或外部卡住的项>

检查：
- 错误或未验证的假设
- 没走的路径和边界
- 回归，以及范围是不是漂了
- 证据能不能撑住所说的目标

返回：
- VERDICT: PASS 或 FAIL
- 只写阻塞问题
- 证据不够的，写明缺什么
```

## 报告

被点名的阶段结束后，只报告这个阶段产出的内容：

- 写了计划，就报告计划
- 做了评审，就报告结论
- 做了执行，就报告改了哪些文件
- 做了验收，就报告带 PASS/FAIL 的证据
- 做了对抗式审查，就报告结论
- 有阻塞，就报告阻塞
- 若有下一阶段，点明，但不要启动

用户要的是完整流程，并且第三方评审、全覆盖验收、对抗式审查都过了，才能说整个开发目标做完了。
